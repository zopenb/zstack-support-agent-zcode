# 查证路由规则

本文件是 ZStack 支持技能的唯一查证路由来源。其他技能只保留入口和强制边界，不复制一套不同顺序。具体支持事件始终从当前事件证据出发；参考系统用于解释、比对和补充，不能替代现场证据。

## 入口判断

| 入口 | 判断标准 | 动作 |
|------|----------|------|
| 低风险直答 | 概念、通用机制或排查思路；不涉及具体现场、版本、错误、兼容性、客户口径或根因 | 直接回答，不查 MCP |
| 最小补充信息 | 缺少组件、版本、静态错误信号或操作路径，无法形成有效故障指纹 | 只问当前路径必需的信息 |
| 单点求证 | 用户明确只问源码、历史案例、文档或外部生态中的一个方向 | 只查指定来源，并只输出该来源能支持的限定结论；只查 GitHub 时不补写 Jira 状态或完整内部版本结论 |
| 支持事件查证 | 客户反馈、日志、告警、失败 API、错误文本、截图转写、版本异常、兼容性或客户回复口径 | 当前事件证据优先；形成去标识化的最小故障指纹后，首批查证 BBS、Jira 和 Confluence；源码/版本类同批加入 GitHub |
| 完整分析 | 用户明确要求完整分析、根因、闭环、交接或研发提报材料 | 执行完整工作流，并保持内部知识系统优先与 GitHub 硬约束 |

具体支持事件不要求用户额外说“分析”。已有证据足以形成静态指纹时主动查证；证据不足时先补最小信息，不进行宽泛搜索。

## 故障指纹与查询安全

先把客户材料整理成两个版本：

```text
内部事件摘要：仅保留分析所需的最小现场上下文，不复制完整日志。
可查询故障指纹：只包含产品/组件、版本范围、静态错误模板、告警名、异常/类/方法名、API 名、配置键和通用操作路径。
```

### 外部查询强制去标识化

向 GitHub、Tavily、公开搜索引擎、厂商论坛或其他公开 Web 发送查询前，删除或泛化：

- 客户、项目、租户、集群、区域、主机、虚拟机、存储、网络等名称；
- UUID、资源 ID、工单号、序列号、订单号、许可证标识；
- IPv4/IPv6、MAC、域名、主机名、邮箱、账号、手机号；
- Token、Cookie、Authorization、URL 查询参数和可能携带身份的文件路径；
- 原始日志上下文、截图文字块、命令完整输出和客户自定义备注。

外部查询只允许使用静态错误模板、异常/类/方法名、API 名、配置键、通用组件名和必要的公开版本号。无法确认某个词是否含客户信息时删除该词。不得把整行原始日志直接作为 GitHub 或 Tavily 查询词。

示例：

```text
禁止：Host 10.20.30.40 vm-prod-01 failed: KVMHost[uuid:...], token=...
允许：KVMHost failed <host-uuid> <ip> + 静态异常名 + 配置键
```

### 内部查询最小化

BBS、Jira 和 Confluence 也只发送命中所需的最小指纹。优先使用静态错误模板、组件、版本和操作路径；除非用户明确授权且查询确实需要，不发送客户名、项目名、账号、UUID、IP、主机名或完整日志。不得发送凭证、许可证内容、原始附件或大段客户材料。

## 内部知识系统优先路由

当前事件证据永远优先。具体 ZStack 支持事件形成去标识化的最小故障指纹后，BBS、Jira 和 Confluence 作为内部知识系统在首批查证中整体查询；它们用于历史比对、缺陷跟踪和内部口径，不能替代当前事件证据。低风险直答、明确单点求证和无法形成有效故障指纹的输入是例外。

| 来源 | 触发条件 | 默认动作 | 不能支持的判断 |
|------|----------|----------|----------------|
| BBS | 具体事件已形成有效故障指纹 | 首批查少量高相关历史案例、差异和可复用验证动作 | 不能单独证明当前根因或修复已生效 |
| Jira | 具体事件已形成有效故障指纹 | 首批查 1-3 个最相关缺陷/需求，只记录编号、标题摘要、状态、组件和版本字段 | 不能单独证明代码已合入、已发布或当前现场命中该缺陷 |
| Confluence | 具体事件已形成有效故障指纹 | 首批搜索相关内部说明、版本边界、兼容矩阵、规范操作、发布说明和产品口径，只读取最小相关摘要 | 不能单独证明当前根因或代码合入 |
| GitHub | 源码机制、调用链、API/配置键/字段下发、类/方法/堆栈、提交、tag、分支、版本合入、版本差异或修复确认 | 与三个内部来源在同一首批查证中查询公开代码与提交；不得等待内部查询结束后再决定是否查询 | 不能证明客户环境实际走了该路径 |
| 官网文档 | 官方配置含义、限制、步骤或产品功能边界 | 按产品版本定位章节；操作、兼容、限制或客户版本边界未知时先问版本，仅概览可并列版本或暂看最新文档并声明不能下版本结论 | 不能替代当前现场证据 |
| Tavily/公开 Web | OS、内核、驱动、QEMU/KVM、libvirt、Ceph、GPU、AI 框架等外部生态 | 使用去标识化指纹，优先官方或厂商一手资料 | 不能单独关闭 ZStack 当前事件 |

路由原则：

1. 对具体事件，当前证据后使用同一个去标识化的最小故障指纹首批查询 BBS、Jira 和 Confluence；不得凭预判跳过其中一个来源。
2. 涉及机制、源码、调用链、字段下发、版本合入或修复确认时，同一首批必须包含 GitHub，不先完成内部查询再进入源码。
3. 查询失败、工具未注入或连接器不可用写“查证未完成”，不能伪装成“未命中”。
4. 内部知识命中高度相同问题时输出处置路径、适用条件和差异校验；只有相似结果时标注“疑似同类”。
5. 完成内部首批查证后，来源已经足以支撑当前回答时停止扩展官网或外部来源；只为实际查询过的来源输出证据块。
6. 来源冲突时保留冲突和各自边界，不挑选更方便的结论覆盖另一来源。

### 高度相似案例

把 BBS/Jira/Confluence 中的记录与当前事件判为“高度相似”前，至少比较：静态错误模板、组件、操作路径、资源类型、版本范围、外部依赖和影响现象。只有这些关键维度无实质冲突时，才给出可复用处置路径；否则标注“疑似同类”，列出差异和补证动作。

## 轻量答复与完整分析

轻量答复用于“能否忽略、是否预期、是否影响、怎么回复客户”等快速场景。查最关键的实际来源后，输出：

```text
结论：
适用条件：
关键断言：[公开标签][E0-E5][来源类型]
影响范围：
建议验证：
客户回复口径：
证据边界：
```

完整分析用于正式根因、闭环、交接或研发材料，执行 Intake、证据映射、安全行动和多维闭环决策。证据模型与闭环字段以 [工作流方法论](workflow-methodology.md) 为准。

## 修复版本与回合确认

用户询问“哪个版本修复、是否发布、是否合入某版本线、fixVersion 是否可信”时，执行以下唯一顺序：

1. **具体事件首批**：同时查询 BBS、Jira、Confluence 和 GitHub。GitHub 查机制入口、相关文件、commit/PR、tag、release branch 或目标分支内容；不得先完成 Jira 再决定是否查 GitHub。
2. **Jira**：查内部跟踪状态、影响版本、fixVersion 和关联项。
3. **Confluence 与 BBS**：Confluence 核对版本边界、兼容口径和内部发布说明；BBS 补充历史现场和验证动作。两者都不能证明代码合入。
4. **单点版本求证例外**：用户明确只做版本单点求证时至少查 GitHub 和 Jira；需要历史现场或内部版本口径时再补 BBS/Confluence。

结论约束：

- 只有 Jira fixVersion 时，只能说“内部跟踪标记/规划为该版本”。
- 只有提交或修复发布存在时，不能把当前事件标成 E5；E5 需要当前事件完成修复后验证闭环。
- 确认“已合入”需要目标 tag/branch 内容、提交可达性或明确发布说明。
- 确认“未合入”需要目标 tag/branch 不含改动、提交不可达、明确排除或明确未回合记录；一次搜索未命中不等于未合入。
- GitHub 未完成时必须写明“不能对是否合入目标版本线下最终结论”。

至少输出：

```text
GitHub 提交/分支查证：
Jira 内部跟踪：
Confluence/内部版本口径：
目标版本线查证：
能确认的事实：
不能确认的事实：
来源冲突或缺口：
```

## 多轮追问

“这个修复、继续查、那 Jira 呢、源码呢、有没有类似案例”等续问继承上一轮的故障对象、去标识化指纹、版本、线索和证据边界。不要从零搜索，也不要复用已经证明不安全的原始查询词。

## Subagent 并行

只有同时满足以下条件才派发 subagent：

- 用户明确要求多 agent、subagent 或并行深查；
- 当前任务可拆成至少两个互不覆盖的有界子任务；
- 当前宿主暴露并允许 subagent 调度工具。

不设置来源数量门槛，也不预设 agent 数量。按本次实际触发的来源分组派发，数量不得超过当前可用并发槽位；主 agent 也占用一个槽位。能由主 agent 同时完成的小任务不为凑数量派发。

推荐的可选分组：

```text
源码/版本：仅 GitHub。
历史案例：仅 BBS。
内部跟踪/口径：具体支持事件查询 Jira 和 Confluence；明确单点例外只查用户指定来源。
文档/外部：仅本次触发的官网文档和/或 Tavily。
```

主 agent 负责当前证据、问题边界、查询词脱敏、结果合并和结论约束。每个子任务都必须携带已经去标识化的查询词；子 agent 不得接收不必要的原始客户材料。等待所有影响结论的子任务；超时或失败标注“查证未完成”，不能写成“未命中”。动态模板见 [显式 subagent 并行深查模板](../../事件分析/references/subagent-prompts.md)。

未触发时只在用户明确要求并行的场景说明原因：

```text
Subagent 状态：未触发
原因：工具未暴露 / 宿主策略不允许 / 任务不可拆分 / 可用并发不足 / 调用失败
降级动作：由主 agent 完成必要查证
```

## 来源状态与输出边界

来源连接状态使用：

```text
工具可见 / 已连接 / 结构化查询成功 / MCP 查询未完成 / 已配置但未注入 / 未配置
```

只有当前会话中的已批准只读工具完成结构化查询，才写“结构化查询成功”。直接远端探测不能证明工具已注入。连接状态不是事件证据等级。

统一参考证据块：

```text
来源类型：当前事件 / GitHub / 官网文档 / BBS / Tavily或公开Web / Jira / Confluence
来源状态：
查询词：仅记录脱敏后的词
命中摘要：
链接：
相关性：高 / 中 / 低
证据成熟度：E0-E5
公开标签：已确认 / 较可能 / 可能 / 证据缺失
能支持的判断：
不能支持的判断：
证据边界：
```

`internal` 是事件分析默认受众。BBS、Jira 或 Confluence 命中时，内部输出必须包含标题摘要和 Markdown 可点击直达链接：BBS 使用 `http://bbs.zstack.io/forum.php?mod=viewthread&tid=<tid>`，Jira 使用 `http://jira.zstack.io/browse/<KEY>`，Confluence 使用 MCP 返回的完整 URL。无法获得完整 URL 时写“直达链接未返回”，不得输出相对链接、只有 tid/key/pageId 的伪链接或猜测 URL。客户输出以及 internal 分析中的“客户回复口径”禁止内部链接、内部端点、原始内部正文、评论和附件；只保留可由对外证据支持的脱敏结论和行动建议。
